最近这两天，AI 圈和开源社区最炸裂的热点，莫过于 Meta 掌门人扎克伯格携手 Alexandr Wang 正式发布的超大前沿模型 **Muse Wonder Full**。

在长程自主软件工程评测（SWE-bench / SWE-Marathon）中，Muse Wonder Full 凭借惊人的端到端自主代码修复能力，**以巨大优势直接双杀打败了同台竞技的 OpenAI GPT 系列与 Anthropic Claude 系列前沿模型**，刷新了业内纪录。

新闻一出，大家最关心的自然是：它到底凭什么能搞定其他模型动辄崩溃的超长程工程任务？

仔细翻看 Meta 披露的技术拆解就会发现，除了算力堆叠外，最关键的架构突破在于两项核心机制：**Active Focus（主动聚焦）** 与 **Active Memory（主动记忆）**。

在过去，几乎所有的 Coding Agent（无论是 Claude Code、Cursor、Pi 还是各种 CLI 编码助手）在执行几十轮的长任务时，都会陷入一种无可奈何的**“结构性健忘”**：
- **规则侵蚀**：一开始你千叮咛万嘱咐：“这个项目必须纯用 Python 基础库和 pygame 纯代码几何绘制，绝对不要引入外部图片素材或外部 asset loader”；Agent 答应得好好的。但改了十几轮代码、修了几个 bug 后，由于上下文长度超标，触发了平台的 Context Compaction（上下文自动压缩裁剪）。这时候你给它派发新需求，它转头就给你塞进一个 `pygame.image.load("assets/bullet.png")`，代码当场报崩。
- **矛盾分裂**：前天你让它“优先用方案 A”，昨天你发现有坑改成了“以后统一改用方案 B”，结果到了今天，它把方案 A 和方案 B 混在一起写，代码里充斥着互相打架的逻辑，甚至两套截然相反的配置项同时在生效。
- **Token 爆炸与迟钝**：要么每轮会话把所有历史和几万行文档硬塞给大模型，既浪费 Token，又引发“大海捞针”般的注意力溃散。

看到 Meta 靠 Active Memory 攻克了这个顽疾，我深受启发。既然原理相通，何不把这套**主动记忆（Active Memory）范式**亲手实现一遍，移植到我们日常就在高频使用的轻量终端 Coding Agent（如 Pi Agent）里？

于是，我编写了这套专为终端 Coding Agent 打造的开源插件与基准套件：
👉 **开源项目主页**：[https://github.com/mongolia19/MuseWonderMemory](https://github.com/mongolia19/MuseWonderMemory)

今天这篇文章，我就抛开那些虚头巴脑的概念，像平时在工位旁边跟大家技术交流一样，聊聊这套主动记忆插件到底是怎么在本地跑起来的，以及我在“坦克大战”和“雷电”两款连续街机游戏复刻的真实 A/B 盲测中，观测到的那些有意思的真实对比。

## 插件的核心思路：记忆不是死文档，而是“有生命周期的不变量”

我们在做真实业务开发时，脑子里记住的并不是这周开会讲的每一句闲聊，而是几条**硬性原则与架构不变量（Invariants）**。比如：
- “这个模块必须保持无状态”；
- “所有异常都要统一抛出定制的 DomainException”；
- “图形全部代码过程化绘制，杜绝任何外部静态文件”。

所以，主动记忆插件的第一件事，就是**把会话中沉淀下来的关键约定结构化提炼出来**，存放在项目根目录下的 `.pi/active-memory.json` 里。每一条记忆长这样：

```json
{
  "id": "mem_9fcbc397",
  "content": "纯几何/代码绘制: 所有图形必须用代码过程化生成，杜绝任何外部图片或字体资源文件",
  "category": "preference",
  "tags": ["几何", "代码", "绘制", "pygame", "primitives"],
  "createdAt": 1791965703620,
  "hitCount": 2
}
```

在 [`.pi/extensions/active-memory.ts`](https://github.com/mongolia19/MuseWonderMemory/blob/main/.pi/extensions/active-memory.ts) 中，核心架构采用了**双环认知引擎（Dual-Loop Cognitive Architecture）**：

```
                       用户输入 / 新任务
                               │
                               ▼
        ┌──────────────────────────────────────────────┐
        │  System 1: 快环检索与动态注入 (<10ms)       │
        │  • Jaccard 词元重合度 + 关键词倒排索引       │
        │  • 严格过滤已废弃 (supersededBy) 规则        │
        │  • 仅将最相关的 Top-K 条军规前置注入工作帧   │
        └──────────────────────┬───────────────────────┘
                               │
                               ▼
                    [ LLM 编码执行与修改 ]
                               │
                               ▼
        ┌──────────────────────────────────────────────┐
        │  System 2: 慢环冲突检测与时序消解引擎        │
        │  • 语义去重与聚类                           │
        │  • 冲突消解：大模型语义判别 + 规则代码自动回滚│
        │  • 因果链标记 (supersedes / supersededBy)    │
        │  • 自然语言交互与周期节流控制 (默认每 3 轮)  │
        └──────────────────────┬───────────────────────┘
                               │
                               ▼
                    持久化不变量存储库
                 (`.pi/active-memory.json`)
```

### 1. 双引擎提炼与时序消解（Contradiction Reconciliation）
如果需求变了，旧记忆怎么办？

很多传统的外挂记忆库最怕遇到用户说：“不用 A 了，全面改用 B”。如果只是机械无脑追加，数据库里就会并存 A 和 B，大模型直接“人格分裂”。

插件在每轮对话结束（`agent_end` 钩子）时，会启动冲突检测机制。它采用**大模型与本地规则代码的双引擎架构**：
- **大模型优先**：通过后台流式调用轻量模型，识别当前交互中是否存在“替换、废弃、改用、升级为”等因果迁移意图；
- **确定性规则托底**：在大模型调用超时、欠费或离线断网时，毫秒级降级到本地规则代码（Jaccard 词元重叠分析与模式匹配），保证开发流不中断；
- **打标退役**：一旦确认规则被推翻，旧规则会被打上 `supersededBy` 和 `supersededAt` 标记，**彻底退出活跃检索池**，绝不留在上下文里当僵尸规则，同时保留因果追溯链条。

### 2. 周期节流与自然语言交互控制
冲突检测如果每轮会话都跑一次，对 API 消耗和终端交互延迟都不划算。

插件默认设置了**每 3 轮会话执行一次**时序消解。更实用的是，我给它加上了**自然语言指令直觉控制**：
你在终端对话里随时跟它说一句：
> “把冲突检测间隔设为 5 轮”
或者
> “每轮都进行冲突检测与因果追溯”

插件内置的正则引擎 `parseReconciliationIntervalDirective` 会自动捕获并把配置持久化到 JSON 文件里，完全不需要你去手改配置文件或者重启 Agent。

### 3. 前置动态注入（Proactive Injection）
在 Agent 每次接收用户新指令之前（`before_agent_start` 钩子），插件会计算当前用户输入与记忆库中所有未废弃不变量的**关键词重合度（Keyword Relevance）**，并结合**时间新鲜度（Recency Weight）**，挑选出关联度最高的 Top-K 条记忆，作为前置约束轻量注入。

只给模型喂当前最关心的 2~3 条军规，既不浪费上下文窗口，又能一针见血地框住边界。

## 真实战场：坦克大战与雷电的连续 A/B 盲测

为了检验这套插件是真有用还是心理安慰，我们在项目中搭建了一组严格的端到端对照实验：
- **实验组（Treatment）**：开启 `active-memory.ts` 插件的 Pi Agent；
- **对照组（Control）**：完全原生、不带主动记忆的普通 Pi Agent。

任务设计为两个连续高难度需求，全部在**各自原会话中一路往下跑**，中途不清理会话上下文：
- **阶段一**：从零编写红白机经典《坦克大战》（4 种坦克、6 种道具、对称地图、纯几何绘制、无界面自检）。
- **阶段二**：在同一个会话中，继续要求复刻经典纵向卷轴射击《雷电》（宇宙背景、至少 5 种敌机、三阶段血条 Boss、黄色机枪/导弹/激光三系升级、同种连吃三颗满级、吃到异种弹药重置归 1 级、无界面自检）。

经过从头到尾的真实编码和自动化 QA 测试，跑出来的结果让人印象极为深刻。

### 1. 代码紧凑度：主动记忆反而让代码更少

很多人的第一直觉是：注入了记忆，Agent 会不会写出更多死板啰嗦的冗余代码？

事实恰恰相反。因为主动记忆在第一阶段就帮实验组牢牢锁定了“纯代码绘制、无外部资源”的约束边界，Agent 在写第二阶段时思路异常清晰，不需要写大量的兜底兼容、无用抽象或者格式嗅探代码：

| 游戏项目 | 对照组（无主动记忆） | 实验组（带主动记忆） | 差异与变化 |
|---|---|---|---|
| **坦克大战** | 1,899 行 (70 KB) | **1,564 行** (56 KB) | 实验组**代码减少 17.6%** |
| **雷电空战** | 2,396 行 (92 KB) | **2,060 行** (81 KB) | 实验组**代码减少 14.0%** |

代码行数减少了近五分之一，内部逻辑却更具内聚性。

### 2. 两个非常刺眼的业务 Bug

最说明问题的，其实是第二阶段我们在亲自上手玩这两个游戏时，发现的两个极其具象的玩法差异。

因为在第二阶段下发雷电任务时，用户提示词很简明，只罗列了 7 项核心升级与敌机要求，**并没有重复啰嗦街机射击游戏的基础常识**。

这时候，两组的表现出现了断崖式的分化：

#### Bug 1：没有保险炸弹（B键大招）
- **对照组（无记忆）**：由于第一阶段坦克大战的上下文太长，在上下文 Compaction 之后，对照组完全丢失了在上一款游戏里形成的“全屏炸弹清屏消弹”的意识。它完完全全照搬了提示词里的字面要求，只做了三种常规枪械，甚至在自动化单元测试里，直接把 `"bomb"` 归为了非法道具：
  ```python
  # 对照组原代码：把炸弹当成了非法道具抛异常
  for bad in ("bomb", "xx", ""):
      try:
          g.player.pickup(g, bad)
      except ValueError:
          pass
  ```
- **实验组（带记忆）**：在 `.pi/active-memory.json` 中，它维持了动作战斗类游戏的道具与防御状态机认知，在生成雷电时，不仅主动保留了 `bombs=2` 默认存量，还完整实现了 `X / K` 键触发的屏幕大招消弹与震屏伤害，甚至包含了 Boss 阶段的消血逻辑。

#### Bug 2：死后弹药等级和死前一模一样（丢失死亡惩罚）
- **对照组（无记忆）**：在实现玩家中弹扣命逻辑 `Player.hit()` 时，写得非常粗糙：
  ```python
  # 对照组原代码
  def hit(self, game):
      self.lives -= 1
      game.clear_enemy_bullets()
      self.reset_position()
      return True
  ```
  玩家死了扣一条命，屏幕一闪复活，手里吃满的 3 级激光或者 3 级导弹依然原封不动。这完全丢失了街机雷电最经典的策略风险机制。
- **实验组（带记忆）**：在 `Player.hit()` 逻辑和单元测试里严格写明了：
  ```python
  # 实验组原代码
  assert (p2.weapon_kind, p2.weapon_level) == ("vulcan", 1), "阵亡后退回机枪 1 级"
  ```
  中弹阵亡即刻回到初始黄机枪 1 级，逼迫玩家在残机复活后重新走位抢箱子。

这两个区别，并不是大模型“智商不够”，而是**长会话下对工程隐式约束的维持能力完全不同**。对照组由于遗忘，变成了只看眼前单句提示词的“字面应声虫”；实验组由于主动记忆的存在，保持了从前序任务延续下来的领域直觉。

## 快速上手与开源仓库

如果你也想在日常使用的 Pi Agent 或类似 Coding Agent 里装上主动记忆，可以直接克隆本项目的开源仓库：

### 1. 克隆仓库与安装依赖
```bash
git clone https://github.com/mongolia19/MuseWonderMemory.git
cd MuseWonderMemory

# 安装依赖并运行 QA 验证
pnpm install
npm test
```

### 2. 挂载扩展到 Pi Agent
把 [`.pi/extensions/active-memory.ts`](https://github.com/mongolia19/MuseWonderMemory/blob/main/.pi/extensions/active-memory.ts) 引入你的项目中：
```bash
pi -e .pi/extensions/active-memory.ts
```

### 3. 自然语言交互体验
在日常编码过程中，你和平时一样给它派发任务即可。它会自动在后台分析提炼有价值的不变量存入本地 `.pi/active-memory.json`。

如果你想调整冲突检测节奏，随时在对话里打一句：
> “冲突检测间隔设为5轮”

它就会自动调整并在后台每 5 轮调用一次因果追溯。

想要查看或者手动编辑当前记忆？直接打开项目根目录下的 `.pi/active-memory.json`，纯明文 JSON，一目了然。

## 写在最后

Meta Muse Wonder Full 在 SWE-bench 上双杀 GPT 和 Claude，向整个行业证明了一件事：**解决长程 Coding Agent 的短板，核心不在于把上下文窗口无限撑大，而在于记忆的高效组织、冲突的主动消解以及架构不变量的持久保持。**

在做这个开源插件之前，我也曾试过各种重型的外部向量数据库和复杂的 RAG 管道，但最后发现，对于日常高频编码的开发者来说，**最有效的工具往往是轻量、透明、就地解决问题的**。

不引入额外的重型运维组件，不强行依赖远程网络环境，把注意力聚焦在“时序演进”和“关键约束提炼”这两个最痛的点上，就能让 Agent 在长达几十轮的连续交付中彻底告别“健忘症”。
